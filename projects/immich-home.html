Immich בבית: גלריית תמונות פרטית על Ubuntu Server

מדריך להקמת שרת תמונות באירוח עצמי על מחשב נייח ישן: Ubuntu Server LTS, ‏Docker Compose ו-Immich, עם גיבוי אוטומטי מהאייפון ברשת המקומית ומשיכה אופציונלית של הספרייה המלאה מ-iCloud. לצד כל שלב מוסבר מה קורה מתחת למכסה, כדי שאפשר יהיה לתחזק את המערכת ולא רק להרים אותה.

ארכיטקטורה

4 CONTAINERS

Immich הוא לא תהליך אחד אלא ארבעה קונטיינרים שמתואמים ב-Docker Compose. הטלפון מדבר רק עם immich-server דרך HTTP. השרת כותב את הקבצים המקוריים לדיסק, את המטא-דאטה ל-Postgres, ומעביר עבודות רקע דרך תור ב-Valkey.

immich-server
שרת API ב-TypeScript על NestJS. מקבל העלאות, מגיש את ממשק הווב, ומריץ את עבודות הרקע: חילוץ EXIF, יצירת thumbnails, ו-transcoding של וידאו עם ffmpeg.
postgres
Postgres 14 עם הרחבות וקטוריות (VectorChord). שומר נתיבי קבצים, אלבומים, משתמשים ומטא-דאטה, וגם את ה-embeddings לחיפוש סמנטי. Immich לא סורק מחדש את תיקיית ההעלאות, ולכן בלי מסד הנתונים הקבצים לבדם הם רק ערימה.
redis (valkey)
Valkey, פורק תואם Redis. משמש כ-backend לתורי BullMQ שמתזמנים את עבודות הרקע. עבודה אחת מפעילה את הבאה: Smart Search וזיהוי פנים רצים רק אחרי שנוצר thumbnail.
machine-learning
שירות Python ‏(FastAPI) שמריץ מודלים בפורמט ONNX: ‏CLIP לחיפוש בטקסט חופשי וזיהוי פנים. רץ בקונטיינר נפרד, כך שאפשר לכבות אותו או להעביר אותו למכונה חזקה יותר.

שכבת החומרה וה-OS

BARE METAL

  1. צריבת ISO והתקנת Ubuntu Server

    מורידים את ה-ISO של Ubuntu Server LTS וצורבים אותו לדיסק און קי עם balenaEtcher. התמונה נכתבת byte-for-byte ומאומתת בסוף. בהתקנה מסמנים OpenSSH server, ומכאן כל העבודה נעשית מרחוק. גרסת Server מתאימה כי אין בה סביבה גרפית שצורכת זיכרון, ו-LTS מקבלת עדכוני אבטחה חמש שנים, כלומר עד 2031 בגרסה 26.04.

    ssh user@<server-ip> מהמחשב הרגיל נכנס לשרת.

  2. לוודא שה-root תופס את כל הדיסק

    בהתקנה מודרכת עם LVM, ה-Logical Volume של ה-root עשוי לקבל רק חלק מה-Volume Group, ושאר הדיסק נשאר לא מוקצה. בודקים ומרחיבים:

    BASH
    df -h /                  # what the filesystem actually sees
sudo vgs                 # VFree > 0 means unallocated space
# default Ubuntu names; -r grows the ext4 filesystem in the same step
sudo lvextend -r -l +100%FREE /dev/ubuntu-vg/ubuntu-lv
    GB מול GiBדיסק של 500GB (עשרוני, ‏10⁹) הוא 465.7 GiB (בינארי, ‏2³⁰). Immich מדווח ב-GiB. ההפרש בין 465.7 ל-456.3 GiB מוסבר במחיצות EFI ו-boot ובתקורה של מערכת הקבצים, כך שאין כאן "מקום חסר".

  3. כתובת IP קבועה

    השרת מקבל כתובת מ-DHCP, ואחרי ריסטארט הראוטר עשוי להקצות כתובת אחרת. האפליקציה ממשיכה לפנות לכתובת הישנה ונכשלת עם Host is down. הפתרון הנקי הוא DHCP Reservation בראוטר, לפי כתובת ה-MAC של כרטיס הרשת, ולא IP סטטי בקונפיגורציית netplan שעלול להתנגש עם טווח ה-DHCP.

    BASH
    ip -br link    # interface name + MAC (e.g. enp1s0)
ip -br addr    # current IPv4

    אחרי sudo reboot הכתובת זהה.

Docker Engine

CONTAINER RUNTIME

Immich דורש את docker compose (Compose v2 כ-plugin). חבילות docker.io ו-docker-compose מהמאגר של Ubuntu עלולות להיות ישנות או להתנגש, ולכן מתקינים מהמאגר הרשמי של Docker עם מפתח GPG חתום:

BASH
sudo apt update
sudo apt install ca-certificates curl
sudo install -m 0755 -d /etc/apt/keyrings
sudo curl -fsSL https://download.docker.com/linux/ubuntu/gpg -o /etc/apt/keyrings/docker.asc
sudo chmod a+r /etc/apt/keyrings/docker.asc

sudo tee /etc/apt/sources.list.d/docker.sources <<EOF
Types: deb
URIs: https://download.docker.com/linux/ubuntu
Suites: $(. /etc/os-release && echo "${UBUNTU_CODENAME:-$VERSION_CODENAME}")
Components: stable
Architectures: $(dpkg --print-architecture)
Signed-By: /etc/apt/keyrings/docker.asc
EOF

sudo apt update
sudo apt install docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin
sudo docker run hello-world
מתחת למכסהקונטיינר הוא תהליך רגיל של Linux שרץ בתוך namespaces משלו (mount, ‏network, ‏PID) עם מגבלות cgroups. לכן לקונטיינר יש מערכת קבצים נפרדת, ותיקייה מהשרת נראית בתוכו רק דרך bind mount שמוגדר ב-volumes. מכאן כלל שחוזר לאורך המדריך: כל נתיב שמזינים בממשק של Immich הוא הנתיב בתוך הקונטיינר, לא על השרת.

Docker עוקף את ufw. פורט שמפורסם ב-ports: נפתח דרך כללי iptables של Docker, גם אם ufw מוגדר לחסום אותו. כדי להגביל גישה צריך לעבוד עם שרשרת DOCKER-USER או לקשור את הפורט לכתובת מסוימת.

הרמת Immich

DOCKER COMPOSE

  1. קבצי Compose ו-env

    BASH
    mkdir ~/immich-app && cd ~/immich-app
wget -O docker-compose.yml https://github.com/immich-app/immich/releases/latest/download/docker-compose.yml
wget -O .env https://github.com/immich-app/immich/releases/latest/download/example.env

    ב-.env מגדירים סיסמת DB אקראית (תווים A-Za-z0-9 בלבד, כדי שלא ישברו את ה-parsing), אזור זמן, ונועלים major version כדי שעדכון לא יקפוץ לגרסה עם breaking changes:

    .ENV
    UPLOAD_LOCATION=./library
DB_DATA_LOCATION=./postgres
TZ=Asia/Jerusalem
IMMICH_VERSION=v3
DB_PASSWORD=ReplaceWithRandomAlnum

  2. הפעלה ובדיקת health

    BASH
    sudo docker compose up -d
sudo docker ps --format 'table {{.Names}}\t{{.Status}}'
sudo docker compose logs -f immich-server     # live logs

    לכל שירות ב-compose מוגדר healthcheck ו-restart: always, כך שהמערכת עולה מחדש לבד אחרי אתחול של השרת. נכנסים ל-http://<server-ip>:2283 ויוצרים משתמש אדמין.

    ארבעת הקונטיינרים immich_server, ‏immich_postgres, ‏immich_redis, ‏immich_machine_learning במצב healthy.

משאביםImmich מגדיר מינימום של 6GB RAM ו-2 ליבות, וממליץ על 8GB ו-4 ליבות. עם 4GB אפשר לרוץ רק כשה-ML כבוי. מגרסה 3, קונטיינר ה-ML על amd64 דורש מעבד ברמת x86-64-v2, שקיימת ברוב המעבדים מ-2012 בערך. עם 16GB אפשר להשאיר את כל ארבעת השירותים פעילים.

ערוץ א׳ · גיבוי מהאפליקציה

הנתיב הראשי

  1. חיבור והגדרת גיבוי

    מתקינים את Immich מה-App Store, מזינים http://<server-ip>:2283, ובוחרים אלבומים לגיבוי. אפשר גם להחריג אלבומים, וזה חשוב ב-iOS כי אותה תמונה יכולה להופיע בכמה אלבומים. בברירת המחדל ההעלאה רצה רק ב-Wi-Fi.

    כדי שהגיבוי ימשיך ברקע צריך להפעיל Background App Refresh. iOS מחליט בעצמו מתי להריץ משימות רקע, ולכן בפועל הגיבוי מתקדם הכי מהר כשהאפליקציה פתוחה.

    מסך הגיבוי מציג "מגובים" שמתקרב ל"סה"כ", ו"בהמתנה לגיבוי" יורד לאפס.

  2. איך נמנעות כפילויות

    לפני כל העלאה האפליקציה מחשבת SHA-1 על תוכן הקובץ ובודקת מול השרת. קובץ שה-hash שלו כבר קיים מדולג. לכן מותר לעצור ולהמשיך, להחליף טלפון או להריץ שוב, בלי ליצור כפילויות. תמונות שנמצאות רק ב-iCloud נמשכות זמנית ל-cache של האפליקציה לפני ה-hashing, וזה צורך נפח ונתונים בטלפון בזמן הגיבוי הראשוני.

Sync v2האפליקציה מחזיקה מסד נתונים מקומי ב-SQLite שמשקף את מצב הספרייה, ומסתנכרנת מול השרת בזרם JSON Lines עם ack tokens, כך שסנכרון שנקטע ממשיך מהנקודה האחרונה. זה אינדקס מקומי של האפליקציה, לא גיבוי: מקור האמת הוא Postgres בשרת והקבצים ב-UPLOAD_LOCATION.

ערוץ ב׳ · משיכה מ-iCloud עם icloudpd

אופציונלי

  1. דרישות חשבון

    icloudpd מדמה סשן של iCloud.com בדפדפן. לכן באייפון צריך להפעיל Access iCloud Data on the Web ולכבות Advanced Data Protection, שמבטל גישת ווב. אימות ה-2FA פג בערך כל חודשיים, ואז צריך להתחבר מחדש.

    פשרה של אבטחה. כיבוי ADP מחזיר את רוב קטגוריות הנתונים ב-iCloud להצפנה סטנדרטית, שבה המפתחות מוחזקים גם אצל Apple.

  2. אימות ראשוני

    BASH
    sudo mkdir -p /srv/icloud-photos/{Photos,config}
sudo chmod 700 /srv/icloud-photos/config    # session cookies live here

sudo docker run -it --rm \
  -v /srv/icloud-photos/config:/config \
  icloudpd/icloudpd:latest \
  icloudpd --username you@example.com --cookie-directory /config --auth-only

    נדרשת סיסמת ה-Apple ID הרגילה וקוד 2FA. סיסמה ייעודית לאפליקציה (App-Specific Password) לא עובדת כאן. אם מתקבל Bad Request (400) בהרצה הראשונה, אפל מכינה את נתוני החשבון ל-API, ומנסים שוב אחרי כמה דקות.

  3. הורדה באצוות ו-cron

    --recent N בודק את N הפריטים שנוספו אחרונים ל-iCloud ומוריד רק מה שחסר. הסקריפט מגדיל את N בכל הרצה, כך שההורדה מתפרסת על פני כמה ריצות ולא מעמיסה על השרתים של Apple בבת אחת:

    /usr/local/sbin/icloud-sync
    #!/bin/bash
# icloud-sync: pull the iCloud library in growing batches
# Usage: sudo icloud-sync [batch size]
set -e

ROOT="/srv/icloud-photos"
APPLE_ID="you@example.com"
BATCH="${1:-100}"
STATE="$ROOT/.batch"

[ "$(id -u)" -eq 0 ] || { echo "root required"; exit 1; }
[ -f "$STATE" ] || echo 0 > "$STATE"
NEXT=$(( $(cat "$STATE") + BATCH ))

docker run --rm --name icloudpd \
  -v "$ROOT/Photos:/data" \
  -v "$ROOT/config:/config" \
  -e TZ=Asia/Jerusalem \
  icloudpd/icloudpd:latest \
  icloudpd --directory /data \
    --username "$APPLE_ID" \
    --cookie-directory /config \
    --recent "$NEXT" \
    --size original \
    --folder-structure '{:%Y/%m}' \
    --set-exif-datetime \
    --no-progress-bar

# advance the window only after a successful run (set -e)
echo "$NEXT" > "$STATE"
    /etc/cron.d/icloud-sync
    # m  h  dom mon dow user command
30 3  *   *   *   root /usr/local/sbin/icloud-sync 200 >> /var/log/icloud-sync.log 2>&1

    אחרי שכל הספרייה ירדה, כדאי להחליף את --recent ב---until-found 20, שעוצר אחרי 20 קבצים רצופים שכבר קיימים ומקצר את הריצה הלילית.

  4. חיבור ל-Immich כ-External Library

    מוסיפים bind mount בקריאה בלבד ל-immich-server. הדגל :ro מונע מ-Immich למחוק או לכתוב XMP sidecars לתיקייה של icloudpd:

    DOCKER-COMPOSE.YML
        volumes:
      - ${UPLOAD_LOCATION}:/data
      - /etc/localtime:/etc/localtime:ro
      - /srv/icloud-photos/Photos:/mnt/icloud:ro
    BASH
    sudo docker compose config >/dev/null && echo "YAML OK"
sudo docker compose up -d
sudo docker exec immich_server ls /mnt/icloud

    בממשק: Administration ← External Libraries ← Create Library, ומוסיפים את הנתיב /mnt/icloud, כלומר הנתיב בתוך הקונטיינר. Immich סורק ספריות חיצוניות פעם ביום, ואת התזמון (בפורמט cron) משנים ב-Administration ← Settings ← External Library, כך שירוץ אחרי icloudpd.

לא להפעיל את שני הערוצים על אותן תמונות. icloudpd עם --set-exif-datetime משנה קבצים שחסר בהם EXIF, ואז ה-SHA-1 שלהם שונה מהעותק שהאפליקציה מעלה. התוצאה היא אותה תמונה פעמיים בציר הזמן. עדיף לבחור ערוץ אחד כמקור אמת.

מספרים וביצועים

הנתונים הבאים לקוחים מבנייה לדוגמה על הרכיבים שתוארו כאן. הם נותנים תחושה של סדרי גודל, ולא יעד שצריך להשיג.

הנתונים מתוך מסך הגיבוי באפליקציית Immich ומדד האחסון של השרת. הממשק באפליקציה ובאתר זמין בעברית.

איפה צוואר הבקבוק

ההעלאה הראשונית של 159.5 GiB לקחה כמה שעות. מי שמסתכל על דיסק SATA ישן עשוי לחשוד בו, אבל החשבון מראה אחרת:

BACK OF THE ENVELOPE
159.5 GiB × 1.0737           ≈ 171 GB
assume ~4 h (14,400 s)       → 11.9 MB/s ≈ 95 Mbit/s

SATA II link  3 Gb/s, 8b/10b   → 300 MB/s
HDD sequential write           → order of 100 MB/s

הדיסק היה פנוי פי 8 בערך. את הקצב קבעו ה-Wi-Fi, ה-hashing בטלפון, ומשיכת מקוריים מ-iCloud לתמונות שלא נשמרו מקומית. HDD כן מורגש במקום אחר: בגישה אקראית. Postgres ויצירת thumbnails עושים הרבה קריאות קטנות, ולכן התיעוד של Immich ממליץ להציב את DB_DATA_LOCATION על SSD מקומי.

גיבוי ושחזור

3-2-1

שרת עם דיסק אחד הוא עותק אחד. Immich לא מגבה את מערכת הקבצים בעצמו, אבל הוא כן יוצר dump יומי של מסד הנתונים ב-UPLOAD_LOCATION/backups כקבצי .sql.gz (ברירת מחדל: כל יום ב-02:00, ‏14 עותקים אחרונים). ה-dump מכיל מטא-דאטה בלבד ולא תמונות, ולכן צריך לגבות גם אותו וגם את הקבצים.

סדר הגיבוי חשוב: קודם מסד הנתונים ואחר כך הקבצים. במקרה הגרוע יהיו על הדיסק קבצים שה-DB לא מכיר, וזה ניתן לתיקון. בסדר ההפוך ה-DB עלול להפנות לקבצים שלא קיימים בגיבוי.

BASH
ls -lh ~/immich-app/library/backups/      # daily .sql.gz dumps
# manual dump, e.g. before an upgrade
sudo docker exec -t immich_postgres pg_dump --clean --if-exists \
  --dbname=immich --username=postgres | gzip > immich-$(date +%F).sql.gz

פינוי מקום בטלפון

FREE UP SPACE

באפליקציה יש פעולת Free Up Space שמוחקת מהמכשיר רק פריטים שכבר גובו בהצלחה לשרת. יש מסך סקירה לפני המחיקה, אפשרויות לשמור מועדפים ואלבומים מסוימים, וקביעת תאריך סף. הפריטים עוברים לתיקיית "נמחקו לאחרונה" של iOS ל-30 יום.

iCloud מסנכרן מחיקות לשני הכיוונים. כשיש iCloud Photos, מחיקה מהטלפון מוחקת גם מ-iCloud ומכל המכשירים. אחרי Free Up Space העותק היחיד הוא בשרת. זו בדיוק הנקודה שבה גיבוי שני של השרת מפסיק להיות אופציונלי. כדאי גם להחריג אלבומים של WhatsApp וכדומה, שמסתמכים על הקובץ המקומי.

תקלות ופתרונות

TROUBLESHOOTING
האפליקציה מפסיקה להתחבר אחרי ריסטארט
ה-IP של השרת השתנה. מעדכנים את כתובת השרת באפליקציה, ומגדירים DHCP Reservation.בלוג האפליקציה: errno 64, Host is down מול הכתובת הקודמת.
הדיסק מראה פחות מקום ממה שצריך
ה-LV של ה-root לא הוקצה על כל ה-VG. ‏sudo vgs ואז lvextend -r.
Immich לא רואה את התיקייה החיצונית
הנתיב שהוזן הוא נתיב על השרת ולא בתוך הקונטיינר, או שהזחת ה-YAML שבורה.docker exec immich_server ls /mnt/icloud מבדיל בין השניים.
icloudpd נכשל אחרי חודשיים
אימות ה-2FA פג. מריצים שוב את פקודת --auth-only.אפשר לקבל התראה במייל עם --smtp-username ו---smtp-password.
כל תמונה מופיעה כשני קבצים
Live Photo נשמרת כזוג של HEIC ו-MOV. זו התנהגות צפויה ולא כפילות.
שגיאות מוזרות ב-docker compose
Docker מותקן מחבילת ההפצה. מסירים docker.io ו-docker-compose ומתקינים מהמאגר הרשמי.

השלבים הבאים

ROADMAP
  • עותק שני של הנתוניםדיסק חיצוני או NAS שמקבל rsync לילי של UPLOAD_LOCATION, ועותק שלישי מחוץ לבית, כדי להשלים 3-2-1.
  • SSD למסד הנתוניםהעברת DB_DATA_LOCATION ל-SSD קטן תשפר את זמני הטעינה של ציר הזמן והחיפוש.
  • גישה מחוץ לביתכרגע השרת זמין רק ב-LAN. הדרך הבטוחה היא VPN כמו WireGuard, לא פתיחת פורט 2283 לאינטרנט.
  • מעקב אחרי icloudpdהפרויקט פעיל אבל מחפש מתחזק חדש, ותלוי ב-API לא רשמי של Apple. מי שמסתמך על ערוץ ב׳ צריך לעקוב אחרי העדכונים שלו.
