Retro Airlocka retro console behind a quarantine

A private retro console on a virtual server (VPS), built as a one-way chain in which each link sees only what it must see. Browsing the download sites happens inside a throwaway container, the downloaded file sits in quarantine until it has a verdict, and the game itself runs on the smartphone, not on the server. The document is both a design explanation and a setup guide.

Lawful use only. The system is intended for games whose copy the operator owns, or for titles under an explicit free license. It runs on a private network and does not distribute files to anyone. The legal details are at the end of chapter 2, in section 3.10 and in the card.
  • A browser isolated in a container, with no write permission anywhere except one folder.
  • The quarantine folder, the only meeting point between the browser and the rest of the system.
  • An active security scanner that runs ClamAV, YARA, a VirusTotal lookup and a content check on every file that lands.
  • The librarian, the service that catalogs scanned games and publishes them to the player.
  • The emulator, which runs on the smartphone and not on the server, so game code is never executed on the server.

1What we are building, and why

The goal is to play old console games on a smartphone, without an app and without a store: open a page and play. For that you need a file, that is, a file containing a copy of a game cartridge or disc, and an that can interpret it.

The problem is not the game but the way to it. Files like these sit on sites that live on aggressive advertising: pop-ups, automatic redirects, fake download buttons that download something else. On such a site one wrong click downloads an executable instead of a game. If that file lands in the regular download folder of the , it sits on the same filesystem that holds everything else: databases, keys, the configuration of other services. The distance between “downloading a game” and “foreign code on the server” is zero.

So the simple solution was ruled out from the start. Not for convenience, but because of one rule worth keeping in every system you build: the blast radius of a small mistake should stay small. A click on an ad is a small mistake. Losing the server is major damage. When the ratio between the two is that bad, you design from the question of what happens when the bad thing happens, not from the question of how to download a file.

Three requirements followed, before a line of code was written:

  • Risky browsing happens inside a throwaway that never returns. Not on the smartphone and not on the operator's computer. If something goes wrong in it, you delete it and bring up a new one from the image, and nothing from the old one comes back. The only thing that leaves it is the downloaded file.
  • No file touches the machine's disk before it has a verdict. There is no in-between state of “scanned, we'll see later”: there are two physically separate destinations, one for what passed and one for what was rejected.
  • The server does not run the game. Ever. It moves bytes, and execution happens somewhere else entirely.

The requirement that the server does not run the game is the heart of the design. An emulator running on the server means game code, downloaded from a site with no reason to be trusted, runs on the machine itself. An emulator running in the smartphone's browser means game code runs inside the browser sandbox, on a different device, with no access to anything on the server. In terms of gameplay these are identical, and in terms of risk they are two worlds. This decision turned the project from a system that runs foreign code into a system that moves files, and without it the project could not have been approved.

The legal side is part of the design itself and not an appendix at the end. The system serves only files whose copy the operator owns, on a private network with a single user, and distributes nothing to anyone. Turning the system into a public demo requires a completely different game library, made up only of titles under an explicit free license, with a license file for each. Section 3.10 explains why there is no live public demo, and what takes its place.

What got built is a one-way chain. Each link is a separate process with a single responsibility, which sees only what it needs to see: an isolated browser, one intake folder, a security scanner that gives a verdict, two separate destinations, the librarian that publishes what passed, and a small server that serves it. The document goes through each link from top to bottom, and explains both the mechanism and the decision behind it. Clicking a technology name opens its full explanation beside the text.

2The risks that came up in the design

2.1 Ad networks and foreign JavaScript in the browser

A browser runs foreign code all the time. Every page that opens runs JavaScript that someone else wrote. On sites that live on advertising, a large part of that code comes from ad networks that nobody has vetted. The scenarios are familiar: an automatic redirect to a fake payment page, a window impersonating a system alert, a download that starts on its own, exploitation of a flaw in the browser itself. The risk is not only that a bad file is downloaded, but that foreign code runs in a context that has access to the cookies, sessions and filesystem of whoever is browsing.

2.2 Malware in the download: what a signature catches and what it does not

The obvious risk. An archive that looks like a game and contains an executable, a file that carries a payload triggered on opening, or a ZIP bomb that inflates until the disk fills up. Here we need to be honest about the limit: a signature engine like catches only what someone has already seen and written a signature for, so entirely new malware passes it. This risk is not closed with a single check but managed in layers, and the assumption that something may get through is part of the design and not a failure of it.

2.3 A symlink in the downloads folder: the compromised browser as a forger

This is the risk that is hardest to see, and so it is also the most interesting. Suppose the browser is fully compromised. What can it do? It can write to the downloads folder, and that is its only privilege. But writing to a folder is not only saving a file. It can place there a named game.zip that points to some internal file. Software that checks “is this a file?” in the usual way will get a positive answer, because the question is answered about the target and not about the symlink. The security scanner would then compute a of the target, send it out to the reputation service, scan the target, rule “clean” (because it really is clean), and move the symlink to the folder that gets published.

The result: internal content becomes something that is sent out and published, without any component doing anything wrong according to its own code. The same idea works with a hard link, with a directory, or with a named pipe that returns different bytes on every read, so that what was checked and what was released are not the same thing. And even without links there remains the time gap: between the moment the file is checked and the moment it is moved, it can be swapped (TOCTOU).

This risk is not theoretical. When tested in practice, a symlink placed in the downloads folder receives a “pass” verdict and is released. The report even records correctly that it is a symlink and what it points to, and on the next line rules “pass”. The information was there, and nobody built a decision on it. So it is worth looking for this pattern in every check you write.

2.4 Extension vs magic bytes: identification by name

A check that relies on the file extension relies on text the attacker chose. There are three separate scenarios:

  1. An executable with an innocent name, for example game.iso that is actually a program.
  2. A double extension, game.iso.exe, which exploits interfaces that hide the trailing extension.
  3. A file whose content is a completely different type from what the name promises, for example an archive with an image's name.

The case where the content is simply not what the name promises is the most dangerous of them, precisely because it does not look dramatic: it is not malware, just a mismatch between name and content, and it is very easy to write a check that flags the case you thought of and misses the rule. The answer is not in the name but in the , the bytes at the start of the file that give away its real type.

2.5 Supply chain: images and tags that move

The system runs other people's software: a community browser , an antivirus engine, a web server, and an emulation library. There are two different exposures here:

  • Images pulled by the latest tag. A future pull can bring a different version from the one that was checked, with nobody having decided on it. The opposite is also true: a blanket pin to a version means security updates do not arrive on their own. There is no safe side here, only a choice between two kinds of risk.
  • An emulation engine loaded from an external CDN. In the early version, the player page pointed to an external address to fetch and its cores. That means that on every game, the smartphone downloaded and ran code from a site outside the operator's control. All of the project's protections guard the file and would not have touched this at all: replacing a file on that side runs foreign code in the user's browser, after all four checks passed successfully.

2.6 Exposure: the internet, the tailnet and the bridge gateway

This is where it is easiest to go wrong, because the intuitive answer (“it only listens locally, so it is closed”) is true in one direction only. There are three separate questions:

  1. Who can reach the services from outside.
  2. Where each container can reach from the inside.
  3. What happens when you share something with another person.

The surprise comes from the opposite direction. A container on a gets an address, and the bridge has a gateway which is the machine itself. Without explicit rules, the container that visits hostile sites can reach services running on the machine, its neighbors on other bridges, the local network, and devices on the private network. When tested in practice from inside the container, a live response came back from the machine's SSH service. In other words, the browser that was meant to be isolated sat in isolation with an inner door.

And there is a human side too: sharing in is at the level of the device, not the port. Adding a friend so they can play means giving them everything that is open on that device, including the quarantine browser and including SSH.

2.7 One machine, one kernel

Everything runs on a single that also runs other services. Two risks follow that have nothing to do with security: a process that eats all the memory triggers the kernel's OOM killer, and the victim may be a completely different service; and a process that pulls CPU without a limit hurts everything else. A graphical browser that streams video is exactly the kind of process that does both.

2.8 Alert flood: a DoS on the mailbox

A system capable of sending a hundred emails a minute is not an system, it is a DoS on the mailbox. After a few such episodes people stop reading, and then the important alert arrives exactly like all the rest and goes unread. The risk here is not technical but human, and that does not make it any less real.

2.9 Silent disk growth: logs, reports and backups

Four places in the system grow without bound: the log, the reports folder, the sealed storage of rejected files, and the browser profile backup archives. Today they are all small. Silent growth does not announce itself: it becomes an outage on the day the disk fills up, and that is usually a day when the operator is busy with something else.

2.10 A persistent browser profile: cookies and cache

In this design the browser profile is kept between sessions, because without it bookmarks, window size and shortcuts are lost, and every use starts from zero. The keeps it in /config, so it survives deletion of the container. The price: cookies, sessions and cache from the very sites this system exists in order not to trust accumulate on disk over time.

Two separate legal matters, easy to confuse, also went into the engineering design and not into an appendix at the end. Rights in the content: a commercial game file is a protected work, and what is permitted with a personal copy is not what is permitted to publish to others. Licenses of the tools: the emulation engine and its cores come under open licenses with obligations, namely attribution and a link to the source code, and one of the commonly used cores prohibits commercial use. Both matters affect engineering decisions, so they were settled at the design stage.

3The solutions and implementation

3.1 Browsing in a container and the intake folder contract

The browser runs in its own . The browser is not installed on the smartphone or on the computer. Instead you watch its screen through , which encodes the screen on the server and streams it to the regular browser you work in. Every redirect, every pop-up and every false click stays there. The container is limited in memory (3 GB) and in number of processes, and is configured with no-new-privileges so it can never escalate privileges. The ceilings were set from a measurement of normal behavior, not from a guess.

The isolation is not worth much without defining the meeting point. The browser has to get a file out, so there is exactly one tunnel: a single folder, attached as a into the browser as its downloads folder, and into the security scanner as its intake folder. The mount is defined once in , and an explicit contract is held against it, because all the security rests on it:

  1. The browser writes here, and this is its only privilege toward the rest of the system. Enforced by: Docker, through the bind mount What rests on it: even if it is fully compromised, this is its only channel
  2. The security scanner reads and deletes from here, and does not write here. Enforced by: the scanner code What rests on it: there is no way for material to travel back toward the browser
  3. Nothing executes files from here. Enforced by: design What rests on it: an executable that lands here is bytes, not a program
  4. Only an entry that is a regular file, with a single name, whose real path stays inside the folder, enters scanning. Enforced by: the scanner code What rests on it: section 3.3, and this clause was added after the problem was proven in testing
  5. A file leaves the folder before any decision is made about it. Enforced by: the scanner code What rests on it: closing the swap window between check and release

3.2 ClamAV, YARA, VirusTotal and the content check: the verdict logic

Every file goes through four independent checks, with a structure check on top that adds a flag. The idea is not that any one of them is perfect, but that each has a different blind spot, so the combination covers more than the sum of its parts.

Content type
Reads the magic bytes and compares them with the extension, through . Blind to extensions that have no unambiguous signature, which means most formats. A mismatch between families sets FAIL, and any other suspicion flag downgrades to REVIEW.
Signatures
receives the file as a stream over the internal network and unpacks archives itself. Blind to anything without a signature, meaning new or targeted malware. A detection sets FAIL, and a communication error sets REVIEW and not PASS.
Pattern rules
with 748 rule files compiled once at startup, with a time ceiling of 120 seconds per file. Blind to patterns nobody wrote a rule for. A match sets FAIL.
Reputation
is queried by the alone, and the file itself never leaves the machine. A file nobody has seen gets “unknown”, which is neither a good sign nor a bad one. One engine or more that flagged the hash sets FAIL.
Archive structure
How many entries are inside, how large it inflates, and whether an executable sits there. The ceilings: 2000 entries and 2 GB unpacked. Implemented for ZIP archives, and other formats rely on the signature engine's internal unpacking. The result is a flag only, that is, REVIEW.

The four possible verdicts, and what each does in practice:

PASS
All checks are clean. The file moves to the clean folder, and it is the only destination that is ever reached.
REVIEW
Suspicious, or too large for a deep scan, or the check itself failed. Sealed in internal storage, and only the report remains on the regular filesystem.
FAIL
Malware was identified, or the content contradicts the extension. Sealed in internal storage, and only the report remains on the regular filesystem.
REJECT
The entry was never a valid file to begin with. Deleted without being opened, and only the report remains.

The direction of the tightening is the main point here. The natural tendency of code is to move forward when something fails: the check returned an error, so carry on. Here the direction is deliberately reversed. An error in a check is a reason not to release. That is the difference between a system that fails safe and a system that fails silently.

3.3 lstat, O_NOFOLLOW and REJECT reports: the intake check

This is the central fix of the project, and it needs a precise explanation because it closes a whole class of bugs and not a single bug. The difference between two system calls is the root of the whole story: stat answers what is at the end of the chain, that is, it follows the symlink to the target, whereas lstat answers what the thing itself is. Every rests on that one call alone, and these are the rules in order:

  1. An entry that is a symlink does not get in. Rejected immediately, and deleted without touching the target The risk closed: the attack proven in testing, where one file is checked and another is released
  2. A directory is not a download. Rejected by entry type The risk closed: a directory inside a downloads folder is a way to hide structure
  3. A named pipe is not a file. Rejected by entry type The risk closed: reading from it hangs or supplies different bytes on each read, so the check and the release see different things
  4. A socket or device file is rejected on the same line. Rejected by entry type The risk closed: reading from a device is not reading a file. There is nothing to scan, and something to break
  5. The link count must be 1. Rejected if greater than 1 The risk closed: a hard link, that is, the same bytes under a second name through which they can be changed
  6. The real path sits directly in the intake folder. Rejected if the resolved path leaves the folder The risk closed: escape through a path component that is itself a symlink
  7. All checks run twice: at discovery, and again after the stability wait. Enforced by: the scanner code What rests on it: closing the swap window, a classic TOCTOU

On top of these rules there are two layers that user code cannot bypass:

  1. The file is opened with the O_NOFOLLOW flag, an explicit request to the kernel to refuse to open if the entry is a symlink. Enforcement sits in the kernel, not in the scanner's code.
  2. Immediately after opening, a check is made on the file descriptor itself, and the result is compared to the facts collected earlier: the same inode, the same device, a regular file, a single name. If anything changed between the check and the open, the operation stops.

And then, before the checks even begin, the file leaves the browser's reach: it is copied through the same file descriptor into the scanner's private storage, and deleted from the intake folder. The two folders are different bind mounts, so this is a copy and delete and not a rename, and the browser is left with no path to the copy. From this moment, what is scanned is exactly what will be released. As a double check, the hash is computed again before the transfer and compared with the one measured at the start, and a mismatch downgrades the verdict.

A rejected entry does not vanish silently. A full report is written about it with the entry's facts, namely type, permissions, link count, inode, and the symlink target if there is one. It is removed from the folder in an operation that does not follow symlinks, and a REJECT line is written to the log. This line indicates a break-in, not a fault: a browser does not create symlinks in its downloads folder. If it appears, something inside the container did something a browser does not do, and this is an email with the highest priority.

The exact same rule applies to the librarian, the service that catalogs scanned games and publishes them to the player, even though the problem was proven only in the scanner. This is a fix of a class of bugs, not of a single instance of it.

3.4 libmagic and the EXPECTED_MIME mapping: content vs extension

The first check that was written flagged a single case: content that looks like an executable under an innocent extension. It worked, exactly in the case it described. When an archive with an image's name was tested, it got a smooth pass with no flag at all, even though the system knew correctly both what the name promises and what the content is.

The solution is an explicit mapping named EXPECTED_MIME: for every extension that has an unambiguous signature, it records which MIME type it promises. measures the content, and the mapping determines whether the measurement contradicts the name. ROM and disc extensions are not in the mapping, on purpose, because they have no signature and so any rule on them would produce noise. The gap is handled at two levels:

  • A mismatch between families, such as an archive with an image's name or a program with a document's name, is a FAIL in itself, and is sealed like malware. There is no judgment call here: if the name lies about the family, the file does not continue.
  • A mismatch within the archive family, such as a compression format wearing the name of another format, is a note only. This is a common, legitimate pattern in real downloads, and the file continues to be judged by the other checks, with the note recorded in the report.

A broader rule follows: a check that flags only the case you thought of should be written as a mapping, not as a condition. A condition covers a case. A mapping covers a class, and what is missing from it is visible.

3.5 Supply chain: a local EmulatorJS and a CSP that blocks the way out

is downloaded once, from a tagged release of the upstream project, and kept locally under a path that carries the version number 4.2.3. Alongside it is kept MANIFEST.sha256, which holds a for each of the 133 files, and next to that PROVENANCE.txt, which records where everything came from and under which tag. An upgrade is not a pull, but a new folder with a new version number, verified against the hashes, and then replacing a single path in the page.

There is a subtlety here. The engine itself still contains an update check in its code, and also a fallback of the kind “if the file is not found locally, fetch it from the network”. That is, even after everything was brought to the machine, code paths remained that can reach out. So a layer is added that does not depend on the behavior of the code: a CSP on the player page with connect-src 'self', which tells the browser that the page may open connections to its own origin only. When tested in a real browser, the update check is indeed sent and indeed blocked, and the game loads all the way. That is the difference between removing the call and making it impossible.

Regarding the base images: the recommendation is to record the hashes of what is running now and to replace the rolling tag with them, but together with a manual monthly update routine. Pinning without an update routine is not a solution, it merely trades one risk for another.

3.6 Tailscale only, and two iptables layers

No port of the system is bound to all network interfaces. All three ports are bound to the machine's loopback only, and access from the smartphone arrives through , which listens on the network's private address and forwards inward. On the open internet the system simply does not exist.

That handles the inbound direction. For the outbound direction, the one in which the container reaches out, a two-layer was built. First, a practical problem had to be solved: the bridge interface name is derived automatically from the network ID, and changes every time the network is recreated, so any rule written against it quietly goes stale. So the bridge name is fixed in the configuration file. A rule that depends on a name that changes is a rule that will stop working on the day you need it most.

  1. Toward the machine itself. New connections from the bridge to the machine are blocked. The word “new” is the point: replies to connections the machine itself initiated keep passing, so regular access from the smartphone is not broken, but the path from the container to the local services is closed.
  2. Toward everything else. Traffic from the bridge to the private address ranges, to the cloud metadata address and to the private network range is blocked. On top of all of these sits one rule that restores what must keep working: traffic within the same bridge, namely the scanner to the signature engine, and all other internal conversations.

What stays open on purpose: browsing the public internet, signature updates, and the reputation lookup. After installation you go back and check exactly what was checked before it: from inside the container, the machine's SSH service no longer answers, the reputation service answers, the internal emulator server answers, and the scanner talks to the signature engine. Verifying a firewall is a list of what is blocked and a list of what still works, otherwise it may be that something that should keep working was blocked too, and nobody knows.

As for sharing: so that another person can play without getting the whole machine, the configuration contains an additional service that does not come up on a regular start, behind a flag. It is an independent node on the private network that serves the arcade and the arcade only. Sharing it shares exactly one thing. This is a separation of responsibility at the identity layer, instead of arguing with a sharing model that works at the device level.

3.7 Resource ceilings: memory, processes and CPU

Every service has explicit ceilings in : memory, number of processes, and for the emulator server also CPU. The kernel's cgroups enforce them, so they are not a recommendation. The ceilings are not a guess but were set from a measurement of normal behavior, with some margin. The aim is not to prevent a fault but to limit who suffers from it: a service that goes out of control hurts itself and not its neighbors on the same machine, and on a single all services are neighbors.

3.8 Alert throttling: a ceiling, a merge window and transparency

The layer sends only bad verdicts. PASS is completely silent, and that is a decision: a system that notifies even when everything is fine trains the operator to ignore it. On top of that sit three rules:

  1. A ceiling of six emails per rolling hour. Beyond that, they are counted and not sent.
  2. Merging an identical finding for an hour. The identification key is a hash of the log line without the timestamp, so exactly the same finding is not sent twice.
  3. Suppression transparency. Every email that does go out carries in its body how many alerts were suppressed since the previous one.

Suppression transparency is the rule that holds up the other two, because throttling without reporting is blindness that looks like quiet. The state is kept in a file, so restarting the service does not reset the hour and does not open the tap again, and the that sends a daily digest reads the same state file.

3.9 tmpfs, profile reset and the rollback routine

The browser's cache sits in tmpfs, that is, in memory only. A cache from sites there is no reason to trust is exactly the kind of data you do not want to survive. The profile itself stays, because giving it up makes the system inconvenient, but it is deleted automatically once a month and manually after every bad verdict. The deletion is run by a on the , and the reset script is built in the right order: first it refuses to run if a download is in progress, then it saves an archive of the profile, and only then deletes and restarts. A timer that knows how to give up a run when the conditions are not right is worth more than a timer that always succeeds.

Alongside this is a routine for the way back: before every rebuild, tag the image that is currently running with a dated rollback tag. If the new build breaks something, going back is a single command. The cost is disk space for a week, and that is a good trade.

3.10 Public exposure: a static site vs a live tunnel

Anyone who wants to show the project publicly faces three options. This is a decision that is very easy to make for the wrong reasons, so it is worth writing all three against each other before choosing.

The recommended option is a static site: an explanation page, real, sanitized scan reports, and a demo that plays in the browser with games under a free license, served from the hosting provider's and not from the machine itself. It adds zero to the attack surface: no new listener, no new route, and no DNS record pointing at the machine. The viewer gets everything: the story, the topology, the code, and a game that works.

The option of exposing the live emulator server through a public tunnel was rejected, because it opens a public route into the machine, every byte served is machine CPU, and headers and error pages become intelligence about the environment. What the viewer gains from it is exactly nothing: a static demo and a live demo look identical in the browser. The option of exposing the isolated browser or the security scanner to the internet is ruled out in advance, because it is equivalent to an open proxy that browses from the machine's address, and to uploading malicious files into a parser that runs on the machine, all for the sake of an effect lasting a few seconds.

Three rules follow from this for every future exposure decision:

  1. What is not visible does not justify a risk. “It runs live on the server” is a sentence that does not appear in anyone's browser.
  2. Sharing is a unit, not a port. When you want to share one thing, you build it a separate identity instead of relying on filtering.
  3. A clean room, not censorship. A real working folder contains machine names, internal addresses, paths and details of other people. You do not publish an existing folder after deletions, but export an explicit list of files into a new folder. Deleting from inside a long document is a leak waiting for one missed line.

In the same spirit, the legal side is closed too, as part of the same exposure decision: the system serves only files whose copy the operator owns, for personal use, on a closed network, and distributes nothing. A public demo requires a completely different library, made up solely of homebrew titles that have an explicit license file, with the license itself, the creator's name, the source address and the file's hash kept for each title. The emulation engine comes under the GPL-3 license, which requires attribution and a link to the source code, and the cores have licenses of their own, one of them prohibiting commercial use and therefore unsuitable for any context connected to work. These checks are done before the page is built, not after.

4The components, one by one

4.1 Firefox in a container: linuxserver.io and Selkies

This is the only that touches the hostile internet by choice. Inside it runs a tiny graphical desktop with , and the streaming layer, , carries its screen to the browser the user is sitting in front of and returns input in the opposite direction. To the user it is a tab. To the machine it is a video stream, and no code from the site that was visited reaches the user's device.

What it is
A full graphical browser in a container, viewed remotely through a regular browser
Image
A ready-made community image from linuxserver.io that includes the browser and the streaming layer, about 3 gigabytes
Reads
The internet; its saved profile
Writes
The downloads folder, which is the quarantine intake folder, and the profile
Not allowed
To reach the services on the machine, neighbors on other bridges, the local network or devices on the private network, all blocked in the firewall; to escalate privileges; to exceed 3 GB of memory or the process ceiling; to leave a cache on disk

Selkies environment variables, and the reason for each value

  1. Manual resolution lock: disabled. Enforced by: Selkies on the server side What rests on it: the client on the smartphone measures the real size of its window and asks for it. A server-side lock rejects the request, and every device gets the screen of another device
  2. Client-side image scaling: on. Enforced by: the client in the browser What rests on it: the server sends a lower-resolution image and the browser stretches it to full size. On a machine with no graphics card this saves real encoding work, and the result looks almost identical
  3. CPU encoding: declared explicitly. Enforced by: an environment variable in the Compose file What rests on it: this machine has no graphics card. The software would detect that on its own; the explicit declaration keeps a future image pull from silently sliding onto a hardware path that does not exist
  4. FPS ceiling: 30. Enforced by: Selkies, before negotiation with the client What rests on it: before it was limited, the client negotiated up to over a hundred FPS, for browsing. No game runs on this channel, because games run on the separate emulator server, so 30 is enough for reading and scrolling and cuts the encoding load to roughly a half to a third
  5. Client sidebar: on, with four buttons. Enforced by: the client in the browser What rests on it: touchpad mode, that is, two-finger scrolling instead of dragging, which is critical on the smartphone; an on-screen keyboard; full screen; and a display settings panel, which is the manual emergency hatch if the automatic resolution negotiation fails on a particular device
  6. Shared memory: 1 GB. Enforced by: Docker, in the container definition What rests on it: the browser uses shared memory between its tab processes. Docker's default is much smaller, and the browser crashes without it

The resolution lock has a story that serves as a general lesson. In the early version the display broke on the smartphone, width and height were locked, and it worked. The note that was recorded was “must lock”. Months later the display broke again, on both the smartphone and the computer. In the container's log a line was found saying that the server rejects client requests to change resolution. That is, the software had been updated, the client had learned to measure itself, and the old fix had become exactly the cause of the fault. After the lock was removed, a real client asked for and received its real size.

Two lessons follow: measure before concluding, and more importantly, every claim recorded in documentation should carry the date and the measurement that produced it. Otherwise a measurement that was correct last year becomes a law that nobody checks anymore.

4.2 The security scanner: the quarantine loop and the verdict

The component that gives the verdict. About 600 lines of Python, in a loop: every two seconds it looks at the intake folder and handles what is in it. First the intake check, then a stability wait, in which the file must stop growing, then staging in private storage, and then the four checks and the verdict.

What it is
A Python service written for the project, which manages the quarantine and gives a verdict to every file
Image
Built in the project from a Dockerfile: Python with for type detection, for pattern rules, and a client
Reads
The intake folder; the rules folder, read-only; its own private storage
Writes
The clean folder; the reports folder and the log; the sealed storage of what was rejected
Not allowed
All capabilities are dropped; it has no ports and nobody can reach it; it does not execute any file it checks; it does not follow symlinks; it does not send a file out, only a

Two small details change the character of the tool:

  1. A temporary file of a download still in progress is never opened, only checked from the outside, and the log records when a download started and when it was cancelled. That way the log tells the story of the whole download and not only its end.
  2. For every file one JSON report is written, containing the name, size, scan time, hash, a dictionary with a sub-dictionary for each check, a list of flags, the verdict and the reasons.

The log is a record of events, and the reports are a record of the latest state for each name. Two different counts that answer two different questions, and they are easy to confuse.

4.3 ClamAV: the signature engine and size limits

What it is
, a free antivirus engine that runs in the background as a daemon and receives files as a stream
Image
The project's official image
Reads
The stream the security scanner sends to it; a configuration file attached to it read-only
Writes
Its signature database, in a separate volume that persists between runs, about 169 megabytes
Not allowed
It has no port published to the machine; it is reachable only to containers on the same bridge; it does not touch the machine's regular folders

Two important things about it:

  1. It unpacks archives itself, so sending it an archive also scans what is inside.
  2. Its size limits in the default configuration are much lower than the size of a modern disk image, and this is a fault that actually happened.

When a large file was sent to it, ClamAV closed the connection on its side, the scanner received a communication error, and according to the rule that an error is not a PASS, the file was sealed as if it were infected. The result looks like a detection, but it is a fault. The fix was to raise the size limits in a configuration file attached to the container. A safe failure is still a failure, and it must be identified by the reason in the report and not by the verdict.

4.4 The librarian: four gates before publishing

The librarian takes only from the clean folder, verifies that the archive is sound, extracts what is needed, and updates the library. Every five seconds it computes a signature of the clean folder, that is, name, size, inode, link count and permissions for each archive, and compares it to the previous one; a change triggers a rebuild. This signature too is computed without following symlinks.

What it is
A Python service written for the project, which turns “a file that passed the checks” into “a game in the library”
Image
Built in the project: Python with archive libraries
Reads
The clean folder, in a read-only
Writes
The folder and the library manifest; rejection reports in the reports folder
Not allowed
All capabilities are dropped; it has no ports; it cannot change or delete anything in the clean folder, so a suspicious entry there is a report only and not an action; it does not publish an archive whose structure was not verified

The gates themselves, in order: entry check, the exact same rule as in the scanner; real type by , because ROM downloads are often an archive of one type wearing the name of another, and the reason is documented in the code: the extension is a suggestion, the bytes are a fact; structural integrity, that is, an integrity check of every member in the archive, plus a check that every member name is a plain relative path, with no absolute path, no drive letter, no .. and no backslash, as protection against an archive designed to write outside the extraction target; and the presence of a recognized ROM inside, without which it skips silently. The rule: only an archive whose structure is verified end to end may be published. It replaces a naive rule you can run into: “if we managed to open it, publish it”.

After the gates, the library logic begins, and it divides the world into two families of consoles:

Cartridges
13 extensions: SNES, NES, three generations of Game Boy, Genesis, N64. One file is extracted from the archive and served raw, because a cartridge game is a single small file, and the browser receives exactly what the core needs with no unpacking work
Discs
9 extensions of handheld and desktop disc-based consoles. Nothing is extracted: the whole archive is copied and the browser unpacks it on its side, because a disc game is often several files that point to each other, for example a cue sheet and data tracks, and extracting one of them breaks the link

Two corners were learned only from real use: two ambiguous extensions can belong to either of two systems, so there is a default based on what is more common and a manual override dictionary for each unusual game; and one generic extension is a single console when alone, but a disc track when it sits next to a cue sheet. This knowledge cannot be invented from the spec, only discovered by running it.

And a point that is recorded as a weakness and not as a feature: to find cover art, the librarian contacts a public image repository with the file name. That is, a process that is entirely internal, with no ports, nevertheless reaches out, and on the way reveals to a third party what is in the library. The right solution is to separate cover fetching into a separate tool that runs on demand, and to leave the librarian fully offline.

4.5 nginx and EmulatorJS: the player server

here is a very small web server, and it is the component most worth copying a template from. It is the definition of a disciplined service: it serves bytes and does nothing else.

What it is
A static web server that serves the library page, the player, the local and the game files
Image
A minimal official image, about 69 megabytes
Reads
The site folder and the configuration file, both in a read-only bind mount
Writes
Three working folders only, all in tmpfs. It writes nothing to disk
Not allowed
Its entire rootfs is read-only; all capabilities are dropped and four are added back with justification, to listen on a privileged port and to drop the worker processes to an unprivileged user; ceilings of 256 megabytes, one core and 128 processes; it does not run or interpret any game file

Its configuration file has five mechanisms, and each answers a specific risk:

  1. Rate limit: 25 requests per second per origin, with a short burst allowance.
  2. A ceiling on concurrent connections: 25, together with the rate limit as flood containment.
  3. Three hardening headers, which stop the browser from guessing content types, send navigation without an origin header, and forbid embedding the pages in another site.
  4. Cache policy by content type: the library manifest is not cached at all because it must always be current, the game files are cached for a month and marked immutable, and the local engine is cached for a year because its path carries a version number.
  5. The cross-origin isolation headers, which are explained right below.

Cross-origin isolation: headers for three heavy cores only

This is the most sophisticated part of the project. Heavy cores need SharedArrayBuffer, which exists only in an isolated page. But an isolated page cannot load resources from another origin without explicit cooperation, and the library page loads cover art from an external repository and a font from a font service. That is, enabling isolation across the board would have fixed the player and broken the library.

The solution: the server defines a mapping on the URL parameter that indicates which core is requested. For the three heavy cores, the two isolation headers get a real value. For any other value they get an empty string, and nginx simply does not send an empty header. The result: the same server, the same origin, and a policy that is activated only for games that need it. Cartridge games keep working exactly as before. This design respects both the new requirement and what already worked.

And on the client side sits a service worker. Its division: heavy and constant things, that is the engine, the cores, the game files and the images, are cached and served from the cache immediately; pages and the library manifest are fetched from the network first and fall back to the cache only when there is no connection. It also does not cache opaque responses, that is, ones the page is not allowed to read, because under isolation they are blocked anyway and would only take up space.

What it is

Three severity levels divide the findings:

  1. A finding of malware or of a contradiction between content and extension is critical.
  2. A finding that needs a human eye is a warning.
  3. An entry rejected at intake is critical, with explicit wording that it is a sign of a break-in through the browser, because that is its real meaning.

4.7 br-fq and iptables: what the browser container can reach

What it is
One internal for all the services, and two firewall layers on the machine side
Image
None. It is a definition in the file, and a systemd unit with a rules script
Reads
A fixed interface name set in the configuration, and not a random name that changes with every recreation of the network
Writes
Firewall rules in two tables: one for traffic to the machine itself, one for traffic passing through it

Three facts to verify after every change:

  1. No port is bound to all network interfaces.
  2. Access from outside passes only through the private network, in both IPv4 and IPv6, and anyone who checks only one of them sees half the picture.
  3. From inside the browser container, the machine's services do not answer while the public internet does.

4.8 systemd timers: profile reset and refusing to run during a download

What they are
One continuous service, the alerts layer, and one monthly that resets the browser profile
Image
None. User-level systemd units, that is, without root privileges
Reads
The intake folder, to know whether it is permitted to act now
Writes
A backup archive of the profile before every deletion
Not allowed
To run while a download is in flight, in which case they exit with an explicit error code; and to delete before backing up

The timer runs on the 1st of every month. It is recommended to run it manually after every bad verdict as well, because that is exactly when the profile touched something nobody wanted it to touch.

Here too is the blind spot of this whole system, and it is documented explicitly: all the layers of protection are silent when they work, and exactly as silent when they do not. A dead scanner looks exactly like a scanner that found nothing. So there is a liveness test: downloading the standard test file of the antivirus industry, and then checking that it was sealed and that one email arrived about it. It is run after every rebuild, because a protection mechanism that has not been tested since it was changed is not a protection mechanism, it is an assumption.

5The system as one unit: end-to-end flow

5.1 A real run: 15 seconds from download to library

The example is a single download from the test run: a 5.0 megabyte archive containing a Game Boy Advance game. Its name here is Space Rescue.zip. All times are taken from the log and from file timestamps, not from estimates. The checks that appear in the timeline are content detection with , signature scanning with , pattern rules, and a reputation lookup in by only.

  1. 10:21:11ScannerThe file finished and its size stabilized. A “scan start” line is written with the size, 5.0 megabytes. Before this line the entry had already passed the intake check and been staged in private storage, that is, it was already out of the browser's reach
  2. 10:21:11Check 1File type by magic bytes: archive. The extension promises an archive. No masquerade, neither between families nor within the family. The description saved in the report also includes the uncompressed size of the content, 8 megabytes
  3. 10:21:11–18Checks 2 and 3The signature engine scanned the archive and what is inside it, and returned clean. 748 pattern rule files ran and returned zero matches
  4. 10:21:11–18Check 4The hash, and only it, was sent to the reputation service. The answer: the hash is known, zero engines flagged it as malicious, 62 engines found nothing in it
  5. 10:21:18ScannerVerdict PASS. The hash was computed again and compared with the one measured at the start, and only then was the file moved to the clean folder. A full JSON report was written with the four checks
  6. 10:21:23LibrarianThe clean folder's signature changed, and a rebuild began. The entry passed the same intake check, the real type was verified by magic bytes, the structure was verified member by member, the member names were checked, and inside was found a Game Boy Advance cartridge file. It was extracted at its full size, 8 megabytes, into the games folder
  7. 10:21:26LibrarianThe library manifest was rebuilt: 25 games, sorted by system and name. From this moment the game appears on the smartphone on a page refresh
  8. NoneAlerts layerComplete silence. A healthy verdict produces no email. Had this been a FAIL, one critical email would have gone out within seconds, subject to the cap of six per hour

Total: fifteen seconds from the opening line in the log to the game in the library, of which seven were in the scan. Most of that time is the network query to the reputation service; the local checks are cheap.

And what would have happened otherwise: if the signature engine had detected something, or if a pattern rule had matched, or if the name had promised an image and the content had been an archive, the file would have been sealed in internal storage, would never have reached the regular disk, and an email would have gone out. If the signature engine had not been available at all, the verdict would have dropped to REVIEW and not risen to PASS. And if the entry in the intake folder had not been a regular file, it would have been deleted without being opened, and the email would have been worded as a sign of a break-in.

6The build recipe, step by step, and the technology index

Before you start

  • A Linux machine with root privileges, for example a VPS. In this design there is no graphics card, so the remote browser's image encoding is done on the CPU.
  • Free memory according to the ceilings: 3 GB for the browser, 3 GB for ClamAV, 2 GB for the scanner, 512 MB for the librarian and 256 MB for the player server (section 3.7). ClamAV holds almost a gigabyte of memory just for the signature database.
  • Docker and Docker Compose installed on the machine.
  • A private Tailscale network that the machine and the smartphone are joined to.
  • A VirusTotal lookup by hash available to the scanner, and an existing email-sending service on the machine for the alerts.
  • A lawful game library: games whose copy the operator owns, or titles under a free license.
  • Code for the scanner and the librarian. These two services are not ready-made tools but small Python code, written to the contracts in the document (sections 3.1 to 3.4, 4.2 and 4.4). The document details the rules, the decisions and the key excerpts, not full code.

The order below is the setup order. Each step is checked before adding the next, and each step ends with a “done when” criterion.

  1. Docker, Compose and a fixed-name bridge

    Install Docker and Compose, and define one bridge for the whole system. Already here, give the bridge a fixed name in the configuration, before there is anything to connect to it, because every future firewall rule will rely on it.

    In the examples in the document every service has the prefix fq- (short for file quarantine) and the bridge is called br-fq. You can choose another prefix, as long as the bridge's fixed name is identical in the Compose file and in the firewall rules. Details: sections 3.6 and 4.7.

    Done when: the network exists, the interface name is the one that was set, and it stays the same name after the network is recreated.

  2. ClamAV with a healthcheck and size limits

    This is the slow service to come up, because pulling the signature database at the start takes minutes, so it comes up at the start of the chain and the other services are configured to wait for it. Raise its size limits in advance, otherwise large files will fail in transfer and look like a detection.

    Details: sections 3.2 and 4.3.

    Done when: the healthcheck is green, the signature database has been downloaded to a separate volume, and the service log shows a signature update from today.

  3. The quarantine folders and two managed storages

    Create three folders on the machine, intake, clean and reports, and two separately managed storages, sealed and private to the scanner. At this stage you write the intake folder contract on paper, before writing code.

    Details: sections 2.3 and 3.1.

    Done when: you can explain, for each of the five points, who writes to it, who reads from it, and what happens if someone else tries.

  4. The security scanner and the intake check, before there is a browser

    Write the scanner and run it on files you place by hand. The internal development order matters: first the intake check and staging, and only then the checks. An excellent check on a file that is not the file that will be released is worth nothing.

    Details: sections 3.2 to 3.4 and 4.2.

    Done when: four cases give four different, documented results. A valid archive moves to the clean folder. The antivirus industry's standard test file is sealed. A symlink, a directory and a named pipe are each rejected with a report of their own, and none of them is opened.

  5. Firefox in a container, connected to the intake folder

    Only now do you add the real consumer. Its downloads folder is the intake folder, its cache is in memory, its ports are bound to loopback, and it has memory and process ceilings set after measuring the idle state.

    Details: sections 3.1, 3.9 and 4.1.

    Done when: a small real download from inside the browser appears in the scan log without manual intervention, and gets a verdict.

  6. iptables in two layers, before connecting the smartphone

    Two layers: blocking new connections from the bridge to the machine, and blocking traffic from the bridge to the private address ranges, with a rule on top that returns traffic within the bridge itself. The rules live in a systemd unit that comes back up on boot, and not in manual commands that disappear.

    Details: sections 3.6, 4.7 and 5.3.

    Done when: from inside the browser container, a service on the machine does not answer, and in the same test: an external site answers, and the scanner gets a response from the signature engine. Both lists, not one.

  7. Tailscale as the only way in from outside

    Join the machine and the smartphone to the private network, and publish the services to it only. No port changes its binding to loopback.

    Details: sections 2.6 and 3.6, and the Tailscale technology card.

    Done when: from the smartphone on the private network the page opens; from outside the network there is no answer at all; and in a check of listeners on the machine there is not a single line listening on all interfaces, not even on IPv6.

  8. The librarian and the four gates

    A read-only bind mount to the clean folder, write access to the site folder, and its own rejection reports. The rule: only an archive whose structure is verified end to end is published.

    Details: section 4.4.

    Done when: a valid archive appears in the library within seconds; a corrupt archive, or one with an out-of-bounds member name, is rejected and a report is written, and it does not reach the games folder.

  9. nginx and EmulatorJS: the player server

    A static server with a read-only rootfs, all capabilities dropped and a few added back with justification, resource ceilings, rate limit, hardening headers, and a cache policy by content type. The emulation engine is kept locally under a path that carries a version number, with a hash for each file, and a CSP that forbids the page from opening any connection outward.

    Details: sections 3.5, 3.7 and 4.5.

    Done when: a cartridge game loads all the way on the smartphone; a heavy core loads and the two isolation headers are returned only for it; and in the browser's network tab there is not a single successful request to an external destination.

  10. Alerts, systemd timers and a rollback tag

    Last, because now there is something to alert on. The alerts layer runs on the machine and not in a container, is rate-limited, and reports how much it silenced. The monthly timer resets the browser profile, and refuses to run during a download. And before every rebuild, tag the existing image with a rollback tag.

    Details: sections 3.8, 3.9, 4.6 and 4.8.

    Done when: a bad verdict produces one email within seconds; a healthy verdict produces nothing; and running the liveness test after a rebuild ends with a sealed file and one email.

Four principles that held all the decisions

  1. Blast radius. Not “will it happen” but “what will burn when it happens”. This is why the ROM runs on another device.
  2. Fail safe. An error in a check is a reason not to release, and not a reason to continue. This direction was chosen explicitly everywhere there is a decision.
  3. Enforcement by mechanism, not by discipline. A read-only bind mount, an open flag the kernel enforces, and a CSP in the browser are worth more than any rule that has to be remembered.
  4. Measure before concluding. Two of the significant faults here were correct fixes of yesterday that became the bugs of today, and neither was found by reading code, only by measuring.
