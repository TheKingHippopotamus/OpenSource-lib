Immich at home: a private photo library on Ubuntu Server

A guide to building a self-hosted photo server on an old desktop PC: Ubuntu Server LTS, Docker Compose and Immich, with automatic iPhone backup over the local network and an optional pull of the full library from iCloud. Each step explains what happens under the hood, so you can maintain the system and not just bring it up.

What you need before starting

PREREQUISITES
  • An old desktop PC to act as the server, with enough disk space for the photo library. The build described here ran on 16GB RAM and a 500GB SATA HDD.
  • A USB flash drive for installation, and balenaEtcher to write the Ubuntu Server LTS ISO.
  • Access to the router, to set up a DHCP reservation for the server.
  • An iPhone with the Immich app, on the same local network as the server.
  • For the optional iCloud channel: an Apple ID, and the ability to turn off Advanced Data Protection.

Architecture

4 CONTAINERS

Immich is not one process but four containers coordinated by Docker Compose. The phone talks only to immich-server over HTTP. The server writes the original files to disk and the metadata to Postgres, and passes background jobs through a queue in Valkey.

immich-server
An API server in TypeScript on NestJS. Receives uploads, serves the web UI, and runs the background jobs: EXIF extraction, thumbnail generation, and video transcoding with ffmpeg.
postgres
Postgres 14 with vector extensions (VectorChord). Stores file paths, albums, users and metadata, as well as the embeddings for semantic search. Immich does not rescan the uploads folder, so without the database the files alone are just a pile.
redis (valkey)
Valkey, a Redis-compatible fork. Serves as the backend for the BullMQ queues that schedule background jobs. One job triggers the next: Smart Search and face detection run only after a thumbnail has been created.
machine-learning
A Python service (FastAPI) that runs models in ONNX format: CLIP for free-text search, and face recognition. It runs in a separate container, so you can turn it off or move it to a more powerful machine.

The hardware and OS layer

BARE METAL

  1. Write the ISO and install Ubuntu Server

    Download the Ubuntu Server LTS ISO and write it to a USB drive with balenaEtcher. The image is written byte-for-byte and verified at the end. During installation, select OpenSSH server; from here on all the work is done remotely. The Server edition fits because it has no graphical environment consuming memory, and LTS gets security updates for five years, which means until 2031 for version 26.04.

    ssh user@<server-ip> from your regular computer gets you into the server.

  2. Make sure root uses the whole disk

    In a guided install with LVM, the root Logical Volume may get only part of the Volume Group, leaving the rest of the disk unallocated. Check and extend:

    BASH
    df -h /                  # what the filesystem actually sees
sudo vgs                 # VFree > 0 means unallocated space
# default Ubuntu names; -r grows the ext4 filesystem in the same step
sudo lvextend -r -l +100%FREE /dev/ubuntu-vg/ubuntu-lv
    GB vs GiBA 500GB disk (decimal, 10⁹) is 465.7 GiB (binary, 2³⁰). Immich reports in GiB. The gap between 465.7 and 456.3 GiB is explained by the EFI and boot partitions and filesystem overhead, so there is no "missing space" here.

  3. A fixed IP address

    The server gets an address from DHCP, and after a router restart the router may assign a different one. The app keeps contacting the old address and fails with Host is down. The clean fix is a DHCP reservation on the router, by the network card's MAC address, rather than a static IP in the netplan configuration, which can collide with the DHCP range.

    BASH
    ip -br link    # interface name + MAC (e.g. enp1s0)
ip -br addr    # current IPv4

    After sudo reboot the address is the same.

Docker Engine

CONTAINER RUNTIME

Immich requires docker compose (Compose v2 as a plugin). The docker.io and docker-compose packages from the Ubuntu repository may be outdated or conflict, so install from Docker's official repository with a signed GPG key:

BASH
sudo apt update
sudo apt install ca-certificates curl
sudo install -m 0755 -d /etc/apt/keyrings
sudo curl -fsSL https://download.docker.com/linux/ubuntu/gpg -o /etc/apt/keyrings/docker.asc
sudo chmod a+r /etc/apt/keyrings/docker.asc

sudo tee /etc/apt/sources.list.d/docker.sources <<EOF
Types: deb
URIs: https://download.docker.com/linux/ubuntu
Suites: $(. /etc/os-release && echo "${UBUNTU_CODENAME:-$VERSION_CODENAME}")
Components: stable
Architectures: $(dpkg --print-architecture)
Signed-By: /etc/apt/keyrings/docker.asc
EOF

sudo apt update
sudo apt install docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin
sudo docker run hello-world
Under the hoodA container is a regular Linux process running inside its own namespaces (mount, network, PID) with cgroup limits. So a container has a separate filesystem, and a folder from the server is visible inside it only through a bind mount defined in volumes. Hence a rule that repeats throughout this guide: every path you enter in Immich's UI is the path inside the container, not on the server.

Docker bypasses ufw. A port published in ports: is opened through Docker's iptables rules, even if ufw is set to block it. To restrict access, work with the DOCKER-USER chain or bind the port to a specific address.

Bringing up Immich

DOCKER COMPOSE

  1. Compose and env files

    BASH
    mkdir ~/immich-app && cd ~/immich-app
wget -O docker-compose.yml https://github.com/immich-app/immich/releases/latest/download/docker-compose.yml
wget -O .env https://github.com/immich-app/immich/releases/latest/download/example.env

    In .env, set a random DB password (only A-Za-z0-9 characters, so they don't break parsing), the time zone, and pin the major version so that an update doesn't jump to a version with breaking changes:

    .ENV
    UPLOAD_LOCATION=./library
DB_DATA_LOCATION=./postgres
TZ=Asia/Jerusalem
IMMICH_VERSION=v3
DB_PASSWORD=ReplaceWithRandomAlnum

  2. Start and health check

    BASH
    sudo docker compose up -d
sudo docker ps --format 'table {{.Names}}\t{{.Status}}'
sudo docker compose logs -f immich-server     # live logs

    Every service in the compose file has a healthcheck and restart: always, so the system comes back up on its own after the server reboots. Open http://<server-ip>:2283 and create an admin user.

    The four containers immich_server, immich_postgres, immich_redis and immich_machine_learning are healthy.

ResourcesImmich sets a minimum of 6GB RAM and 2 cores, and recommends 8GB and 4 cores. With 4GB it can run only with ML turned off. From version 3, the ML container on amd64 requires an x86-64-v2 CPU, which most processors from about 2012 onward have. With 16GB you can leave all four services running.

Ingesting photos

INGESTION

There are two ways to get the library onto the server. The first, backup from the app, is the main path. The second is useful when you want the server to pull from iCloud without involving the phone.

Channel A · app backup

The main path

  1. Connect and set up backup

    Install Immich from the App Store, enter http://<server-ip>:2283, and choose the albums to back up. You can also exclude albums, which matters on iOS because the same photo can appear in several albums. By default, upload runs only on Wi-Fi.

    For backup to continue in the background you need to enable Background App Refresh. iOS decides on its own when to run background tasks, so in practice backup moves fastest when the app is open.

    The backup screen shows "backed up" approaching "total", and the pending count drops to zero.

  2. How duplicates are avoided

    Before each upload the app computes a SHA-1 of the file contents and checks it against the server. A file whose hash already exists is skipped. So you can stop and resume, switch phones, or run it again without creating duplicates. Photos that exist only in iCloud are temporarily pulled into the app's cache before hashing, which uses storage and data on the phone during the initial backup.

Sync v2The app keeps a local SQLite database that mirrors the library state, and syncs with the server over a JSON Lines stream with ack tokens, so an interrupted sync resumes from the last point. This is the app's local index, not a backup: the source of truth is Postgres on the server and the files in UPLOAD_LOCATION.

Channel B · pull from iCloud with icloudpd

Optional

  1. Account requirements

    icloudpd emulates an iCloud.com session in a browser. So on the iPhone you must enable Access iCloud Data on the Web and disable Advanced Data Protection, which blocks web access. The 2FA authentication expires about every two months, and then you need to sign in again.

    A security trade-off. Turning off ADP returns most iCloud data categories to standard encryption, where the keys are also held by Apple.

  2. Initial authentication

    BASH
    sudo mkdir -p /srv/icloud-photos/{Photos,config}
sudo chmod 700 /srv/icloud-photos/config    # session cookies live here

sudo docker run -it --rm \
  -v /srv/icloud-photos/config:/config \
  icloudpd/icloudpd:latest \
  icloudpd --username you@example.com --cookie-directory /config --auth-only

    The regular Apple ID password and a 2FA code are required. An app-specific password does not work here. If you get Bad Request (400) on the first run, Apple is preparing the account data for the API; try again after a few minutes.

  3. Batch download and cron

    --recent N checks the N most recently added items in iCloud and downloads only what is missing. The script increases N on each run, so the download is spread across several runs and does not load Apple's servers all at once:

    /usr/local/sbin/icloud-sync
    #!/bin/bash
# icloud-sync: pull the iCloud library in growing batches
# Usage: sudo icloud-sync [batch size]
set -e

ROOT="/srv/icloud-photos"
APPLE_ID="you@example.com"
BATCH="${1:-100}"
STATE="$ROOT/.batch"

[ "$(id -u)" -eq 0 ] || { echo "root required"; exit 1; }
[ -f "$STATE" ] || echo 0 > "$STATE"
NEXT=$(( $(cat "$STATE") + BATCH ))

docker run --rm --name icloudpd \
  -v "$ROOT/Photos:/data" \
  -v "$ROOT/config:/config" \
  -e TZ=Asia/Jerusalem \
  icloudpd/icloudpd:latest \
  icloudpd --directory /data \
    --username "$APPLE_ID" \
    --cookie-directory /config \
    --recent "$NEXT" \
    --size original \
    --folder-structure '{:%Y/%m}' \
    --set-exif-datetime \
    --no-progress-bar

# advance the window only after a successful run (set -e)
echo "$NEXT" > "$STATE"
    /etc/cron.d/icloud-sync
    # m  h  dom mon dow user command
30 3  *   *   *   root /usr/local/sbin/icloud-sync 200 >> /var/log/icloud-sync.log 2>&1

    After the entire library has been downloaded, replace --recent with --until-found 20, which stops after 20 consecutive files that already exist and shortens the nightly run.

  4. Connect to Immich as an External Library

    Add a read-only bind mount to immich-server. The :ro flag prevents Immich from deleting files or writing XMP sidecars in the icloudpd folder:

    DOCKER-COMPOSE.YML
        volumes:
      - ${UPLOAD_LOCATION}:/data
      - /etc/localtime:/etc/localtime:ro
      - /srv/icloud-photos/Photos:/mnt/icloud:ro
    BASH
    sudo docker compose config >/dev/null && echo "YAML OK"
sudo docker compose up -d
sudo docker exec immich_server ls /mnt/icloud

    In the UI: Administration → External Libraries → Create Library, and add the path /mnt/icloud, that is, the path inside the container. Immich scans external libraries once a day, and the schedule (in cron format) is changed under Administration → Settings → External Library, so that the scan runs after icloudpd.

Do not enable both channels for the same photos. icloudpd with --set-exif-datetime modifies files that lack EXIF, so their SHA-1 differs from the copy the app uploads. The result is the same photo twice on the timeline. It is better to pick one channel as the source of truth.

Where the bottleneck is

The initial upload of 159.5 GiB took a few hours. Looking at an old SATA disk, you might suspect it, but the arithmetic shows otherwise:

BACK OF THE ENVELOPE
159.5 GiB × 1.0737           ≈ 171 GB
assume ~4 h (14,400 s)       → 11.9 MB/s ≈ 95 Mbit/s

SATA II link  3 Gb/s, 8b/10b   → 300 MB/s
HDD sequential write           → order of 100 MB/s

The disk had roughly 8x headroom. The rate was set by Wi-Fi, hashing on the phone, and pulling originals from iCloud for photos that were not stored locally. An HDD does make itself felt elsewhere: in random access. Postgres and thumbnail generation do many small reads, so Immich's documentation recommends placing DB_DATA_LOCATION on a local SSD.

Backup and restore

3-2-1

A server with a single disk is one copy. Immich does not back up the filesystem itself, but it does create a daily dump of the database in UPLOAD_LOCATION/backups as .sql.gz files (default: every day at 02:00, last 14 copies kept). The dump contains metadata only and no photos, so you need to back up both it and the files.

Backup order matters: the database first, then the files. In the worst case the disk will hold files the DB does not know about, which is fixable. In the reverse order the DB may point to files that do not exist in the backup.

BASH
ls -lh ~/immich-app/library/backups/      # daily .sql.gz dumps
# manual dump, e.g. before an upgrade
sudo docker exec -t immich_postgres pg_dump --clean --if-exists \
  --dbname=immich --username=postgres | gzip > immich-$(date +%F).sql.gz

Freeing space on the phone

FREE UP SPACE

The app has a Free Up Space action that deletes from the device only items that have already been successfully backed up to the server. There is a review screen before deletion, options to keep favorites and specific albums, and a cutoff date. Items go to the iOS "Recently Deleted" folder for 30 days.

iCloud syncs deletions in both directions. With iCloud Photos on, deleting from the phone also deletes from iCloud and from all devices. After Free Up Space, the only copy is on the server. This is exactly the point where a second backup of the server stops being optional. Also exclude WhatsApp albums and the like, which rely on the local file.

Troubleshooting

TROUBLESHOOTING
The app stops connecting after a restart
The server's IP changed. Update the server address in the app, and set up a DHCP reservation.In the app log: errno 64, Host is down against the previous address.
The disk shows less space than expected
The root LV was not allocated across the whole VG. Run sudo vgs, then lvextend -r.
Immich does not see the external folder
The path entered is a path on the server and not inside the container, or the YAML indentation is broken.docker exec immich_server ls /mnt/icloud tells the two apart.
icloudpd fails after two months
The 2FA authentication expired. Run the --auth-only command again.You can get an email alert with --smtp-username and --smtp-password.
Every photo appears as two files
A Live Photo is stored as a HEIC and MOV pair. This is expected behavior, not a duplicate.
Strange errors from docker compose
Docker was installed from the distribution package. Remove docker.io and docker-compose and install from the official repository.

Next steps

ROADMAP
  • A second copy of the dataAn external disk or NAS that receives a nightly rsync of UPLOAD_LOCATION, and a third copy off-site, to complete 3-2-1.
  • An SSD for the databaseMoving DB_DATA_LOCATION to a small SSD will improve timeline loading and search times.
  • Access from outside the homeFor now the server is reachable only on the LAN. The safe way is a VPN such as WireGuard, not opening port 2283 to the internet.
  • Keeping an eye on icloudpdThe project is active but looking for a new maintainer, and depends on an unofficial Apple API. Anyone relying on channel B should follow its updates.
